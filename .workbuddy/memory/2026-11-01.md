## 跨集数据覆盖事故（08:53）

**现象**：第 1 集的分镜变成了第 2 集的剧本（老师/学生 · 土木咨询），原面霜剧本消失。

**根因（前端路由参数没被读取）**：
- `ProjectManage.vue` 点某集「创作」时跳转**带了**参数：
  `router.push('/projects/:id/create?episodeId=' + ep.id)`
- 但 `ProjectDetail.vue` 的 `load()` **完全不读这个参数**，写死取 `episodes.value[0]`
- 结果：从第 2 集点进去，页面实际加载的是第 1 集；用户粘贴剧本 → 保存 →
  识别 → 分镜，全部写进第 1 集

**为什么无法恢复**：`identify.go` 的 `DeleteByEpisodeID` 用的是
`Unscoped().Delete()` —— **物理删除**，不是软删除。旧资产和分镜都没了，
库里连 `deleted_at` 记录都查不到。

**修复（`ProjectDetail.vue`）**：
1. `load()` 优先按 `route.query.episodeId` 找剧集，找不到才退回 `episodes[0]`
2. `switchEpisode()` 里 `router.replace` 把集号同步进 URL —— 刷新、前进后退、
   复制链接都停在同一集
3. `ensureEpisode()` 新建剧集时把 `episodes.value = [res.data]`（覆盖）
   改成追加，否则下拉里只剩新建的那一集，切不回别的

**教训**：跳转方带了参数、接收方不读，是最隐蔽的一类「串数据」bug ——
两端各自看都正常，只有联调才发现。凡是 URL 上带了 ID 的页面，
`load()` 第一件事就该是读它。

## 台词被截断「最后一句说不完」（09:23）

**现象**：分镜台词结尾都是半句，如「想清楚这…」。

**实测**：两集各 9 段，其中 4 段（段3/5/7/9）台词全部**断在 53 字**。

**根因**（`storyboard_service.go` 的 `buildVideoPrompt`）：
```go
d.Action = condense(raw, 60)          // 先压到 60 字
splitInlineDialogues(d.Action)        // 再从这 60 字里拆台词
```
`condense` 是给「画面动作描述」限长的工具，拿它截台词等于把后半句砍掉。

**为什么只取消截断不够**：这段台词 80+ 字，按 3.8 字/秒要 21 秒，
塞进 H3 单段 15 秒上限是 5.3 字/秒 —— 嘴跟不上，还是说不完。

**修复**：
1. `buildVideoPrompt`：台词改成从**完整原文**拆（`splitInlineDialogues(raw)`），
   `condense` 只用于 action
2. 新增 `splitLongDialogueFrames` + `packDialogue` + `splitSentences`：
   单镜台词超过 15 秒时按句末标点装箱拆成多帧，每帧 ≤ 15 秒，
   第 2 帧起 Text 加「（续）」，末尾统一 `renumberText`
3. `StoryboardService.Generate` 返回前调用 `splitLongDialogueFrames(drafts, 15)`
4. 测试 `storyboard_service_test.go`：`TestRuleEngineKeepsFullDialogue`
   （台词一字不少 + 每帧 ≤15 秒 + 超长必拆）、`TestRuleEngineKeepsShortFrameIntact`

**注意**：修复只对**新生成**的分镜生效，库里已有的是截断的，要重新生成分镜才更新。

## 首帧生成失败但界面一直「生成中」（10:41）

**现象**：首帧任务已经 failed（上游 `errorCode=805`），弹窗里却一直转圈，用户以为卡死。

**根因（前后端各一半）**：
- 后端 `GET /episodes/:id/firstframes` 只返回 `first_frames` 表，**不含任务状态**
- 前端轮询只能看「`g.image` 有没有变」，任务失败时图永远不变 →
  `done` 永远凑不齐，只能等满 40 次 × 5 秒 = **200 秒**超时才停，
  停下后还只提示「首帧图还在生成，稍后刷新查看」

**修复**：
1. `TaskRepository.LatestByAssetIDs(taskType, assetType, ids)`：按 assetID 取每个资产
   最近一条任务（`created_at DESC` + 首次出现即最新）
2. `FirstFrameHandler.List` 返回 `ffGroupView`（嵌入 `model.FirstFrame` +
   `taskStatus` / `taskError`），前端据此判断真实状态
3. 前端：
   - `isFfBusy()` 排除 `taskStatus === 'failed'`，失败不再算「生成中」
   - 轮询 `done` 判断加上 `taskStatus === 'failed'` → 立即结束，不再干等 200 秒
   - 结束时若有失败组，`toast.error('首帧图失败 N 组', 第一条错误原因)`
   - 卡片上失败态显示红字「生成失败」+ 截断的错误原因（hover 看全文）

**教训**：异步任务的「完成」判断不能只看产物有无 —— 失败时产物永远是空的，
必须有显式的状态位。前后端都该以任务状态为准，而不是靠产物变化去推断。

## 网关取消了任务，本地一直「生成中」（20:59）

**现象**：用户在 RunningHub 后台取消了任务，本地 25 个任务永远卡在 running / 10%。

**根因**（`rh_gateway_generator.go` 的状态分支）：
```go
case "QUEUED", "RUNNING", "":
    continue          // ← 空状态也被当成「还在排队」
```
上游对已取消/过期的任务返回的是 **`status: ""` + `errorCode: "1004"`
（Task not found, please check the task ID）**，状态字段是空的，
所以命中 `""` 分支后无限 continue，永远等不到结果。

**修复**：把 `""` 从「继续等」里拆出来 ——
- 空状态 **且有 errorCode** → 判定失败，带出上游的 errorMessage
- 空状态 **且无错误码** → 偶发抖动，继续等下一轮

**验证**：重启后 `Recover()` 把 25 个 running 任务重新入队续查，
上游一律返回 1004 → 全部转 failed，**自动退款 875 积分**（25 × 35），
前端从「生成中」变成「生成失败」。

**教训**：上游状态机里的「空字符串」绝不能默认当成「进行中」。
空值往往意味着「这个任务已经不存在了」，要结合 errorCode 判断。

## 段间姿态不连贯：段8坐着、段9站着（23:33）

**现象**：段 8 尾帧写「@学生 保持坐姿」，段 9 的站位却成「站在椅子旁」，人物凭空站起来，
后面每段跟着错。

**根因（我自己的设计缺陷）**：`GenerateStream` 里把**第一段的 situation 当「全局站位基准」**
传给后续每一段。第一段是开场（学生站着等老师示意坐下），于是：
- `prevEnd`（上一段尾帧）说「@学生 保持坐姿」
- `baseSituation`（全局基准）说「@学生 站在办公桌另一侧的桌前」

两个输入直接打架，而「整集不变」的措辞比「接着上一段」更强，模型选了后者。

**修复**：
1. **删掉 baseSituation 传递**（`GenerateOne` 传空字符串）——
   位置和姿态只能由 `prevEnd` 一段一段链式传下去，这是唯一真相
2. `expandUserPrompt` 里把**上一段尾帧提到最前面**（模型对开头最敏感），并加硬约束：
   「只有在台词明确要求时才能改变姿态（如角色说『走吧』才起身），
   而且要在对应镜头的 action 里写出触发点；台词没要求就不许改姿态、不许换座」

**实测**（临时剧集，验证后清理）：8 段全部连贯 ——
段 1 学生站着（开场老师示意落座）、段 2 起坐下、**段 3–8 一直保持着坐姿**，
左右位置也没变（老师画面右侧、学生画面左侧）。

**教训**：给 LLM 多个"上下文来源"时，如果它们描述的是同一件事（在这里是人物姿态），
必须明确谁优先，否则它会挑措辞更强的那条，而不是更新的那条。
