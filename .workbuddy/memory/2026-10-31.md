## 修复「分镜卡片 13 秒 / 描述词 3 秒」不一致（22:16）

**现象**：分镜卡片显示 13 秒，但视频描述词里写 `[Shot 1] 0.00–3.00s`「单镜头 3 秒」。

**根因**：`Storyboard.Duration`（卡片显示的秒数）和 `VideoPrompt` 里的 `[Shot N] 起止秒`
是**两个独立存储的值**，没有任何一致性约束：
- 生成时两者由同一份 `FrameDraft` 算出，是一致的
- 但 `PUT /api/storyboard/:id` 允许只传 `duration` 而不同时给 `videoPrompt`，
  于是 Duration 被单独改写后，描述词还停在旧时间轴

**危害**：出片时传给时长节点（132）的是 `Duration`，模型会把 3 秒的动作硬拉成 13 秒，
后 10 秒基本静止 —— 用户会误以为是「模型不动了」。

**实测数据**：该集 6 帧里 2 帧不一致（帧1 13 vs 3、帧3 4 vs 3），其余 4 帧一致。

**修复**：
1. `internal/service/frame_prompt.go` 新增 `RescalePromptDuration(prompt, total)`：
   解析所有 `[Shot N] a.bb–c.dds`，按原比例缩放到 total，最后一段收口防累计误差，
   每段至少 1 秒；同时同步 summary 里的「单镜头 N 秒」/「共 N 秒」
2. `internal/handler/storyboard.go` 的 `Update`：`req.Duration != nil && req.VideoPrompt == nil`
   时自动调用上面的函数重排时间轴
3. 测试 `TestRescalePromptDuration`（单镜缩放、多镜按比例 1:2:3→2:4:6、summary 同步、
   无时间轴/非法入参原样返回、缩到比镜头数还短不出零长度）
4. 用 `PUT /api/storyboard/:id`（只传 duration）修正了库里那 2 帧，现全部一致

**遗留观察**：帧1 现在是 13 秒配 7 个字台词（「这个面霜真的好用，」），
语速只有 0.5 字/秒，出片会明显拖沓。按内容算这段本该 3 秒 ——
`Duration` 理想上应由台词需求决定，工具栏的时长只该当「上限」用。

**结论（22:25 用户实测确认）**：**重新生成整集分镜确实能修好**。
因为生成时 `Duration` 和描述词时间轴由同一份 `FrameDraft` 一次算出，天然一致。

**但重新生成有重副作用，必须提前告知用户**：
`StoryboardRepository.DeleteByEpisodeID` 用的是 `Unscoped().Delete()` —— **物理删除**整集分镜后重建，因此会丢失：
- 已生成的视频（`videoUrl`）
- 首帧图（`firstFrameImage`）与草图（`sketchImage`）
- 用户手工编辑的文案
- 分镜 ID 全部变化；段数也可能变（LLM 重新拆分），`first_frames` 表里按 `frameIndexes`
  存的「场景+机位」分组会对不上

安全替代：只对出问题的那几帧调 `POST /storyboard/:id/regenerate`（只改该帧文案与时长，
不删其他帧、不清视频）；或直接 `PUT /storyboard/:id` 只传 `duration`，走新的
`RescalePromptDuration` 重排时间轴。

## 视频丢失事故与三个根因（22:59）

**现象**：用户出片后服务重启，4 条视频任务全变成「任务中断超过 30 分钟，已判定失败」，视频看不到。

### 根因 1：`Queue.Recover()` 一刀切 30 分钟误杀（`internal/queue/queue.go`）
- 阈值 `staleAfter = 30 * time.Minute`，但 **video 任务超时本来就是 45 分钟**
- 且**没区分任务是否已提交到上游**。有 `externalTaskID` 的任务上游结果 24 小时内可取，
  重新入队会走「续查」（`gen.ExistingTaskID`）而不是重新 `/task/add`，根本不该判失败
- 修复：`hasUpstream := ExternalTaskID != ""` 时**永不判失败**，直接重新入队续查；
  阈值提到 60 分钟（> 视频 45 分钟超时），且只对「连上游 ID 都没拿到」的才算真丢

### 根因 2：`writeBack` 把 duration 硬编码成 13（同一个文件）
```go
case "frame":
    Updates(map[string]interface{}{"video_url": url, "duration": 13})  // ← 病根
```
- 13 是早期默认模型 Seedance 的时长。换成 H3（出 3/5/7 秒）后，
  **每次出片成功都会把分镜的 duration 改成 13**，而描述词时间轴还是 3 秒
- 这才是用户 22:16 问的「卡片 13 秒 / 描述词 3 秒」的**真正来源**
  （之前误判成 `PUT` 单独改 duration 造成的）
- 修复：改成从 `task.Params.duration` 取实际选定时长，取不到就不动

### 根因 3：时长计算有两套算法（`internal/service/frame_prompt.go`）
- `EstimateFrameDuration`（卡片显示）走 `frameDurationNeed`：浮点累加 + 0.4 呼吸 + 统一 ceil
- `BuildFrameVideoPrompt`（描述词时间轴）走逐镜 ceil 再相加
- 8 个字的一句台词，前者算 4 秒、后者算 3 秒 → 卡片 4 / 描述词 0.00–3.00s
- 修复：抽出 `planShotSeconds(shots)` 作为**唯一口径**，两者都用它；
  0.4 秒呼吸改为只加在**最后一镜**（逐镜加会把 3 秒的段撑成 5 秒）
- 新增回归测试 `TestDurationMatchesPromptTimeline`（6 种形态断言 duration == 时间轴总长）

### 数据恢复
上游 3 条仍 SUCCESS（第 4 条 `2116536284680122370` 返回 -3 已过期，救不回）：
- 从 COS 下载到 `~/.jikeai-clone-data/results/{本地taskId}.mp4`（命名规则同 `ResultStore.Save`）
- 用 Python sqlite3 直连改库：`generation_tasks` → succeeded + result_url，
  `storyboards` → video_url（映射：c81e24e2→段1 / 166fe4da→段2 / 50097632→段3）
- 3 条视频经 `/static/results/*.mp4` 验证 HTTP 200
- 积分：每条已退 35，恢复后未回扣（自用系统，账目上多退 105）

**教训**：`Recover()` 这类「重启兜底」逻辑，必须先判断「上游是否已有产出」，
再决定丢弃还是续查。只看本地时间戳会把还在上游正常跑的任务全部误杀。

## 新增整集合成功能（23:07）

用户问「片段都生成好了，是不是要加个合成功能」—— 加了。

**环境**：ffmpeg 8.1.2 已装在 `D:\ffmpeg\bin`，**已在系统 PATH**（`Get-Command ffmpeg` 可见），

**实现**：
- `internal/service/compose.go` — `VideoComposer`：

    报 "No such file or directory" 但路径看着完全正确
  - `ProbeDuration` 用 ffprobe 取时长
- `internal/handler/compose.go` — `POST /api/episodes/:id/compose`（**同步**，
  concat 是秒级，没必要进任务队列）；只拼 `videoUrl` 非空的段，按 `frame_index` 排序，
  跳过的段号在 `skipped` 里返回
- `cmd/server/main.go` 注册路由；`pkg/config` + `config.yaml` 加 `ffmpeg_path`
- 前端 `ProjectDetail.vue` 成片页：顶部「合成整集」按钮 + 成片卡片（播放器 + 段数/时长 + 下载）；
  切剧集时清空 `composed`

**实测**：3 段（7.29 + 4.46 + 4.46 秒）→ 成片 16.24 秒，1088×1920 / h264+aac / 24fps，
**耗时 0.57 秒**，12 MB。`go test ./...` 全绿，`npm run build` 通过。
